# Booking Confirmation and TimeLock Handoff Design

**Date:** 2026-08-25  
**Status:** Approved in chat; implementation pending spec review  
**Scope:** Booking web flow, Google Apps Script booking mutation, and the BookingAiLab-to-WPF TimeLock API contract

## Goal

ทำให้การจองมีผลลัพธ์ที่ผู้ใช้เข้าใจได้ทันทีทุกกรณี และทำให้ข้อมูลที่จำเป็นสำหรับ TimeLock ถูกสร้างและส่งผ่าน Backend อย่างสอดคล้องกัน โดย WPF ไม่อ่าน Google Sheet โดยตรง

## Current findings

- หน้า booking มี success panel และ error text อยู่แล้ว แต่ข้อมูลผลลัพธ์ยังไม่ได้ถูกกำหนดเป็น contract เดียวสำหรับการแจ้งเตือนและ TimeLock
- `create_booking` เขียน `Bookings` และ `Users` ใน Apps Script lock เดียวกัน แต่ยังไม่มี `booking_confirmed` event สำหรับ audit/integration handoff
- `Users` เก็บข้อมูลบัญชี TimeLock ในรูป password verifier และหน้าเว็บแสดง password จริงจาก response สำเร็จเพียงครั้งเดียว
- `/api/timelock/login` ตรวจ username/password กับข้อมูลใน Sheet และสร้าง `session_started` แล้ว แต่ response ยังไม่มี booking end time และ quota ที่ WPF ต้องใช้ตั้ง timer และตัดสินใจต่อเวลา
- Apps Script และ Sheet ยังคงเป็นแหล่งข้อมูลหลัก ส่วน WPF ต้องเรียก BookingAiLab API ที่ตรวจ Device Token

## Design

### 1. Booking result contract

`bookMachineAction` จะคืนผลลัพธ์สองแบบที่ UI ใช้โดยตรง:

```ts
type BookingFormState =
  | { ok: false; code: string; message: string; retryable: boolean }
  | { ok: true; code: "BOOKING_CONFIRMED"; message: string; booking: CreatedBooking };
```

Failure messages จะ map จาก stable server codes เช่น `MACHINE_UNAVAILABLE`, `BOOKING_MACHINE_OVERLAP`, `BOOKING_CUSTOMER_OVERLAP`, `BOOKING_OUTSIDE_SCHEDULE`, `BOOKING_ATOMIC_NOT_CONFIGURED` และ `BOOKING_ATOMIC_FAILED` เป็นภาษาไทยที่บอกการแก้ไขได้ การแสดงผลจะไม่เปิดเผย password หรือข้อมูล verifier เมื่อไม่สำเร็จ

Success data จะมีอย่างน้อย:

```ts
type CreatedBooking = {
  bookingId: string;
  bookingNumber: string;
  machineCode: string;
  startAt: string;
  endAt: string;
  status: "confirmed";
  timelockUsername: string;
  timelockPassword: string;
};
```

UI จะแสดง success panel พร้อมเลขที่จอง, เครื่อง, ช่วงเวลา และข้อมูล TimeLock โดยติดป้ายชัดเจนว่า password แสดงครั้งเดียว มีปุ่มกลับไปดู/จัดการการจอง และมี failure alert ที่คงอยู่จนกว่าจะเริ่มคำขอใหม่หรือจองสำเร็จ

### 2. Atomic Google Sheet booking handoff

ภายใน Apps Script `create_booking` ที่อยู่ใต้ script lock เดียวกัน ให้ทำตามลำดับ:

1. ตรวจเครื่อง, เวลา, วันปัจจุบัน, duration 180 นาที, schedule และ overlap
2. ตรวจ idempotency key ก่อนสร้างข้อมูลซ้ำ
3. append แถว `Bookings` พร้อม `extensionCount = 0`
4. upsert แถว `Users` พร้อม PBKDF2 verifier และ `allowedMinutes = 180`
5. append `Events`:

```json
{
  "eventType": "booking_confirmed",
  "bookingId": "booking-id",
  "machineCode": "PC-001",
  "username": "student",
  "status": "confirmed",
  "payload": {
    "bookingNumber": "BK-20260825-0001",
    "startAt": "2026-08-25T01:30:00.000Z",
    "endAt": "2026-08-25T04:30:00.000Z",
    "allowedMinutes": 180
  }
}
```

6. append `AuditLog` action `booking_confirmed`
7. return booking metadata plus the one-time plaintext credentials generated by the Backend request; never write plaintext password to Sheet, Event, AuditLog, or server log

If any validation fails, no booking/user/event/audit row is created. Duplicate idempotency requests return the original booking data and must not append another confirmation event.

### 3. TimeLock API handoff

WPF continues to authenticate with `x-machine-code` and `x-device-token`; it never receives Google credentials or Apps Script secrets and never reads Sheet directly.

After a successful `POST /api/timelock/login`, the response session will include:

```json
{
  "sessionId": "session-id",
  "bookingId": "booking-id",
  "bookingNumber": "BK-20260825-0001",
  "machineCode": "PC-001",
  "username": "student",
  "startedAt": "2026-08-25T01:30:00.000Z",
  "endAt": "2026-08-25T04:30:00.000Z",
  "allowedMinutes": 180,
  "extensionCount": 0,
  "status": "active"
}
```

The values are resolved server-side from the matching `Users`, `Events`, and `Bookings` rows. WPF uses `endAt` as the authoritative timer and calls the existing extension check/confirm endpoints when the session expires. The server remains authoritative for extension count, midnight boundary, next-booking conflict, and final end time.

### 4. Error handling and retry

- A missing/invalid login returns `AUTH_REQUIRED` and does not attempt a Sheet mutation.
- A stale UI selection is revalidated server-side; a conflict returns an actionable failure and leaves the user on the booking form.
- Google/API failures return a stable failure code and a generic retry message without leaking secrets or raw provider responses.
- The booking mutation uses an idempotency key so a client retry cannot create duplicate booking/user/event records.
- TimeLock login returns stable API codes through the existing `timelockErrorResponse` boundary.

## Testing strategy

Tests will cover observable behavior rather than source text:

- action result success/failure shape and Thai error mapping
- booking UI renders the success handoff and failure alert without exposing credentials on failure
- Apps Script creates Booking, User, confirmation Event, and Audit rows together; invalid/conflicting input creates none; duplicate idempotency does not append another event
- TimeLock login returns booking metadata, end time, quota, and extension count from Sheet-backed records
- API contract rejects malformed input and preserves Device Token and machine isolation
- full test suite, TypeScript, production build, and `git diff --check`

## Security and privacy

- Google Sheet remains private and shared only with the Backend service account
- `Users` stores PBKDF2 verifier fields, never plaintext password
- Plaintext TimeLock password is returned only in the successful booking response and rendered once in the browser
- Passwords, verifier fields, Apps Script secret, and service-account key are excluded from UI errors, event payloads, audit metadata, logs, and Git
- WPF receives only the minimum session and machine data needed for operation

## Out of scope

- Email or push notification delivery
- Direct WPF source changes, because that project is on another computer
- Replacing Google Sheets with another database
- Client-side authority over booking time or extension eligibility
